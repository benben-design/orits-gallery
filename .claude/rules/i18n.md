# Bilingual + RTL

The most invasive constraint in the codebase. Hebrew is the default language and
reads right-to-left; English is secondary and reads left-to-right. Neither is a
translation of the other bolted on afterwards.

## Where languages are defined

`lib/i18n/config.js` is the single source of truth. It holds the locale list,
the default, direction per locale, display names, and BCP-47 tags. Routing,
static params, the `<html>` attributes and the language switcher are all derived
from it.

**Adding a language must stay as close to a two-step job as possible:** add the
code to the config, add `lib/i18n/locales/<code>.json`. In application code that
still holds absolutely — if a change would require editing a third place in the
app, that change is wrong. Put the knowledge in the config instead.

Never enumerate `['he', 'en']` by hand anywhere in the application.

**There is now one exception, and it is in the database.** `orders.buyer_locale`
carries a check constraint listing the supported locales, because SQL cannot
read a JavaScript module and a `CHECK` has to hold literals. So adding a third
language is a **three**-step job: the config, the locale file, and a migration:

```sql
alter table orders drop constraint orders_buyer_locale_supported;
alter table orders add constraint orders_buyer_locale_supported
  check (buyer_locale in ('he', 'en', 'fr'));
```

The constraint is named rather than auto-named precisely so that this stays two
lines. The trade was taken deliberately — an order with a typo'd language is an
invoice that never arrives, and the database is the only layer that can refuse it
whatever writes the row — but it is a real cost and it is written down here so
that the third step is not discovered the hard way.

## URL shape

The locale is the first path segment. The bare root redirects to the default
locale. Build internal links with `localeHref(locale, path)` — no component
should be assembling locale-prefixed URLs by string concatenation.

The language switcher uses `replaceLocaleInPath` so the user stays on the same
page in the other language. Sending someone to the homepage because they changed
language is a bug.

On an artwork page the two languages have different slugs, so a plain segment
swap produces the other language's URL still carrying this language's slug —
`/en/art/לימונים`. That is handled on the **server**, not in the switcher: the
artwork route resolves a slug in any language via `findWorkByAnySlug` and
redirects to the canonical one. The switcher therefore needs no knowledge of
paintings and no client-side data fetch.

`getSlugsForWork` returns one work's slug in every language. It is not used by
the switcher; it is what the `hreflang` tags should use when they are added
(seo.md).

Two traps that break this, both hit for real:

- **`localeHref` percent-encodes the path — use it.** A raw Hebrew slug is
  legal inside an `<a href>` but illegal in an HTTP `Location` header, so
  `redirect()` throws `ERR_INVALID_CHAR` on an unencoded one.
  **It encodes the path only, and carries a `?query` through untouched**, which
  it did not always do. Encoding the whole string turns `?` and `=` into
  literal characters inside a path segment and the URL stops being a query at
  all: the gallery's two category filters were built through here and shipped
  as `/he/gallery%3Fcategory%3Dlandscape`, so every filter on the gallery was a
  dead link that 404'd. Pass a query when you need one; do not assemble the
  locale prefix by hand to avoid this function.
- **Never set `dynamicParams = false` on the `[locale]` layout.** It applies to
  the whole subtree, so the artwork route's cross-language slugs 404 before they
  can redirect — which silently breaks the switcher on every artwork page.

## Direction and document language

`dir` and `lang` are set once, on the `<html>` element, derived from the locale
via `getDirection` and `getLocaleTag`. Never set `dir` on an inner element to
"fix" a layout, and never hardcode `rtl` anywhere.

**There is one exception, and it is the opposite case.** The admin's preview at
`/admin/works/[id]/preview` renders the public artwork page inside the admin's
Hebrew document, and it can be asked for the English one. That fragment is
genuinely in another language, which is what `dir` and `lang` on an element are
*for* — it is not a layout being patched. Direction resolves per element, so
every logical property in the body below the wrapper lays out exactly as it will
on the site, which is the whole point of previewing it. The values still come
from `getDirection` and `getLocaleTag`; nothing is hardcoded.

Consequences for CSS, which are not optional:
- Use logical properties — `margin-inline-start`, `padding-inline-end`,
  `inset-inline-start`, `border-inline-start` — not `left` / `right`.
- Use `text-align: start` / `end`, not `left` / `right`.
- Flex and grid follow the writing direction automatically; do not counteract it.
- Icons that imply direction (arrows, chevrons, "back") must flip. Icons that do
  not (a cart, a close X, a play triangle) must not.
- Numbers, prices and Latin brand names stay left-to-right inside Hebrew text.

## Strings

Every user-facing string lives in `lib/i18n/locales/he.json` and `en.json`.
No literal copy in a component — not even placeholder text, not even a single
word, not even in the admin area.

Both files must always have the same key set. A key that exists in one language
and not the other is a bug, not a "todo".

`getDictionary(locale)` is **server-side**. Resolve strings on the server and
pass them down to client components as props rather than loading dictionaries in
the browser.

## Content in two languages

Painting data is bilingual at the field level, not the record level. Title,
description, medium and slug each exist per locale on the same record. There is
one painting, with two language faces — never two records.

The admin must therefore capture both languages for every text field, and the
UI should make a missing translation visible rather than silently falling back.

### The English is written for her, and she signs it off

She works in Hebrew. Leaving a Hebrew title or description in the admin form
translates that whole field in one go and fills its English twin — through
`lib/translate.js`, on the server, never from the browser, and never while she
is still typing. The provider is a language model, so the module sends an
instruction rather than a string, and the two fields get different ones: a title
has to come back a noun phrase, a description as prose. Her Hebrew travels as
the user turn and is never concatenated into that instruction.

The part that matters is not the translation. It is that **a filled-in
translation arrives unapproved, and the form does not save while anything is
unapproved.** She either approves it as it stands or edits it, and editing
counts as approving because she has read it either way. Without that gate this
is a way to publish English nobody ever looked at, which is worse than an empty
box: an empty box is visibly missing, and a confident bad translation is not.

Three properties keep it from being infuriating, and all three are form state —
no column, and what gets saved is simply the text she approved:

- **Automatic translation only ever replaces text the machine itself put
  there.** The moment she types in an English box it is hers, and editing the
  Hebrew again leaves it alone; the button beside it is how she asks for a
  fresh translation, which arrives unapproved like any other. A **stored**
  English value counts as hers too — the record cannot say whether she wrote it
  or approved it, and guessing wrong destroys a sentence she wrote.
- **A failure is not a trap.** No key, a key the provider refuses, a timeout or
  a rate limit all come to the same thing: no translation arrives, nothing is
  pending,
  and she types the English and saves exactly as she would have before. The
  English title is required and the English slug derives from it, so that path
  has to stay open.
- **Nothing is translated on load.** Opening a work and tabbing through it
  changes nothing and spends nothing: translation follows an edit to the
  Hebrew, not a visit to the field.

Two fields work differently, and both are deliberate:

- **Medium is not bilingual content.** In the database it is a **closed set of
  keys** — `oil-on-canvas`, `pastel-on-paper` — and the display strings are
  translated in the application like any other UI string. So it belongs in the
  locale files, not in the painting record — and both keys now have entries in
  `he.json` and `en.json`, under `medium`, and
  `components/ui/mediumLabel.js` is the one place that turns a key into those
  words — a component reading `work.medium[locale]` directly prints
  "oil-on-canvas" at a visitor. Adding a third medium is therefore a
  migration *and* two locale entries. It is also optional: there is no key
  meaning "not recorded yet", so the sixteen seeded works carry none, and the
  admin's medium field offers an explicit "not recorded" choice that stores
  null rather than inventing one.
- **Alt text falls back rather than blanking.** Per language and optional; when
  absent, the application derives it from the work's title in that language.
  Deliberately not defaulted in the database, because a default would be a
  Hebrew or English phrase stored outside the locale files.

## The buyer's language is recorded, not inferred

An order stores the language the buyer was reading when they placed it, and it
is required. The confirmation and the tax invoice have to arrive in that
language.

It cannot be reconstructed afterwards. It is not the site default — most buyers
are not on the default. It is not derivable from a shipping address, because an
Israeli address says nothing about which language someone reads. And it is not
`Accept-Language` months later, because that was never stored. Capture it during
the checkout request or it is gone.

## Formatting

Use `lib/format.js`. It formats prices and dimensions with a fixed locale tag so
the server and the browser always produce identical output. Do not call `Intl`
directly in a component with the machine's default locale, and do not format
dates from `new Date()` at render time — both cause hydration mismatches.

## Hebrew slugs

Hebrew slugs are non-ASCII and arrive URL-encoded. Always `decodeURIComponent`
before matching — the repository already does this, so go through it.
