# File Map

What exists, what it owns, and when to touch it.

**Keep this file current.** When you add a route, a component, or a lib module,
add its row here in the same change. A stale map is worse than no map — it is the
first thing read at the start of a session.

## Config

| File | Role |
|---|---|
| `CLAUDE.md` | **Intentionally empty. Leave it that way.** The rules in `.claude/rules/` are picked up on their own; anything written here is also read by the separate planning session, which must keep its own role. See workflow.md |
| `next.config.mjs` | **Declares the `X-Robots-Tag: noindex, nofollow, noarchive` headers on `/admin` and `/dev`** — in the framework rather than in `netlify.toml`, because the host applies its own header rules only to responses it serves from its store and never to one a function produced, and every admin route is server-rendered. Both the bare path and the wildcard are listed for each tree. Also image pipeline sizes, tuned for the future sharp scans rather than today's stand-ins. Also points `images.loaderFile` at `lib/image-loader.js`, which is what lets hosted and local paintings be resized by different services at once. **`images.loader` is deliberately left at its default** — `'custom'` 404s `/_next/image` and would break all sixteen local files — and there is deliberately **no `remotePatterns`**, so a hosted image falling through to the built-in optimiser throws instead of quietly costing money |
| `netlify.toml` | **The whole of the host's build configuration, and deliberately four settings.** The build command exactly as `package.json` defines it, and `NODE_VERSION = "22"` — pinned because the host's default Node moves with its build image, and a major version changing underneath a build is a failure that arrives on a day nothing was pushed. **The other two narrow Netlify's secrets scan rather than disabling it**: `SECRETS_SCAN_OMIT_PATHS` names Turbopack's build cache and nothing wider, because that cache records environment values and is never served, and `SECRETS_SCAN_OMIT_KEYS` names `CLOUDINARY_CLOUD_NAME` and nothing else, because the cloud name is public. They are here rather than in the UI so the exception can be seen in the diff; see deployment.md. Framework, publish directory and function bundling are all detected. **Response headers are deliberately not in here** — see `next.config.mjs`, and deployment.md for why the distinction matters |
| `jsconfig.json` | The `@/*` path alias |
| `eslint.config.mjs` | ESLint flat config — `eslint-config-next/core-web-vitals` plus ignores. Not wired into the build |
| `package.json` | Scripts. `prebuild` regenerates the image manifest; `lint` runs ESLint then the contrast, admin-guard, sitemap and image-crop checks; `dev:placeholders` regenerates the `/dev` placeholder images; `seed:local` fills a local database. Two runtime dependencies beyond Next and React: `pg`, and `lucide-react` for icons — the second is a deliberate reversal of an earlier decision, recorded in code-style.md |
| `.env.example` | **Committed template listing every key the project will need**, dummy values only, `DATABASE_URL` first. The real `.env.local` is git-ignored. `DATABASE_URL` and `ADMIN_SESSION_SECRET` are read today, and `GEMINI_API_KEY` is read when it is there. `NEXT_PUBLIC_SITE_URL` is read too, and a production build fails without it. The three `CLOUDINARY_*` keys are read as a set by `lib/image-host.js`, for uploading only — serving an image that already exists needs none of them; only the three `HYP_*` payment keys are unread — their names are settled now that the provider is, and nothing imports them yet |
| `.gitattributes` | Stores every text file as LF regardless of the checkout platform, and marks image/font binaries. Landed in the first commit precisely so it never has to renormalize the tree later |

## Data — `lib/data/`

| File | Role |
|---|---|
| `works-repository.js` | **The only painting data module pages may import.** Product-shaped, all async, plain objects out. Two reads see drafts — `getWorkById` and `getWorksForAdmin` — and everything else is published-only, `getWorksByIds` (what the cart is built on) included: an id that no longer resolves is simply absent from the result, and that difference is how the cart knows a painting has gone. **Reads every painting from Postgres** through `lib/db.js`, converts agorot to shekels in the one place that conversion happens, and requires each read to state whether it is public or admin scope so a draft cannot leak by omission. `setMainImage` is the one write that touches `work_images`: delete-then-insert in a transaction, because the database allows one main image per work and inserting first fails the index. **`getGalleryWorks` is the one cached read** — `unstable_cache`, tagged, one hour — and it is deliberately **not** a cache on `getAllWorks`, which `app/api/health/route.js` calls precisely to prove the database is reachable and `app/sitemap.js` calls too. **`markWorkSold` and `returnWorkToSale` are the pair the works list is built on** — two columns each, no validation, and both excluding `sale_channel is distinct from 'this-site'` in the `where` clause rather than reading the row first, so a sale that answers for an order cannot be overwritten or undone by hand and there is no check-then-act window |
| `work-input.js` | Also owns `IMAGE_PUBLIC_ID_FIELD`, the name of the field a photograph chosen before a work exists travels in — a constant because the panel writes it and the action reads it, and two literals is how they stop matching. It is deliberately **not** validated here: what it holds is an identifier at the image host, and only the host can say whether it means anything. **Validates a painting submitted from the admin**, and owns the vocabulary the form builds itself from — including `MANUAL_SALE_CHANNELS`, the channels the artist picks by hand, which excludes `this-site` because checkout writes that one. Pure — no database, no React — and loadable by plain Node, so the rules can be exercised without starting the app. Returns error *codes*, never sentences, because the Hebrew lives in the locale files. Owns `slugify`, which is Unicode-aware so a Hebrew title produces a Hebrew slug, and it is where shekels become agorot on the way in |
| `artworks.js` | **The seed fixture, not storage — and running it now destroys real data.** Its records still hold the absurd stand-ins, and `seed:local` upserts on `slug_en` over every column, so running it against a database carrying the real catalogue replaces the titles, prices, sizes, media and descriptions with placeholders and reverts the images to local paths. Migration 008 is the way back. `scripts/seed-local-database.mjs` is its only consumer for data, via `readAllRecords()`. It also holds `WORK_STATUSES`, `WORK_CATEGORIES` and `IMAGE_TYPES` — the repository re-exports the first two, so deleting this file breaks the running site as well as the seed. Off limits outside `lib/data` except that script. Its JSON import carries `with { type: 'json' }` so plain Node can load it — remove that and the seed script breaks. See data-layer.md |
| `image-manifest.json` | Generated. Real pixel dimensions per painting. Never hand-edited. Authoritative over the database's copy **for the images that are in the repository** — a reference beginning with a slash. Anything stored elsewhere reads `work_images.pixel_width` / `pixel_height` instead, which is a decision made per image rather than a rule for the site |

## Lib

| File | Role |
|---|---|
| `lib/format.js` | `formatPrice`, `formatDimensions`, `formatDateTime` — fixed locale tags so server and client agree. Treats `price.amount` as **whole shekels**, which the database does not. `formatDateTime` additionally **pins the timezone to Asia/Jerusalem**: the dev server runs in the artist's timezone and a deployed one in UTC, so an unpinned formatter renders a late-evening order on the wrong day depending on which machine drew the page |
| `lib/delivery.js` | **The one place the delivery rate is written.** The two methods as a closed set (`shipping`, `self-pickup`), the flat rate in **agorot** (4000 — minor units, so nothing converts between here and the column), `isDeliveryMethod` for validating at the boundary, and `needsShippingAddress`. Pure — no database, no React, loadable by plain Node. **It answers "what would we charge now"; only `orders.delivery_fee_agorot` answers "what did we charge then"**, which is why changing the rate here cannot rewrite an old order. `deliveryFeeAgorot` **throws** on an unknown method rather than falling back to free — the opposite of `getStatusPresentation`, deliberately: a display fallback costs nothing, a money fallback silently waives a charge. Destined for `/admin/settings`, which is the whole reason it is a module rather than a literal in the checkout |
| `lib/auth/password.js` | **The only place a password is hashed or checked.** scrypt from `node:crypto`, no dependency. Writes a self-describing `$scrypt$N=...$salt$key` value so the cost can be raised later without resetting passwords, and compares with `timingSafeEqual`. `needsRehash` is for a login that upgrades a password in passing — nothing calls it yet |
| `lib/auth/session.js` | **The session token, signed and verified.** Pure functions, no cookies and no request — HMAC-SHA256 over `{ sub, exp }`, keyed on `ADMIN_SESSION_SECRET`. Owns the cookie name, the `/admin` path and the 14-day life. The signature is checked before the payload is believed. **The no-session-table trade is written here and in security.md** |
| `lib/auth/admin-session.js` | The request-facing half: `startAdminSession`, `endAdminSession`, `readAdminSession`, `isSignedIn`. The one place the cookie's attributes are set, so setting and clearing cannot disagree. Server-side only — it reads an httpOnly cookie |
| `lib/auth/admin-guard.js` | **The page guard.** `requireAdminSession(path)` — no session, no render: it redirects to the login page carrying where you were going. Signature and expiry only, no database. Also owns `safeReturnTo`, which narrows that path to somewhere inside the admin so it cannot become an open redirect. Its docblock records *why* the guard is per-page rather than in a layout, and both facts were measured |
| `lib/auth/login-throttle.js` | **The sign-in rate limit.** Counters in Postgres, never in memory — serverless hosting's many short-lived instances make an in-memory counter reset at random. Keyed on address *and* source, with a looser per-source ceiling. Owns the ladder as plain constants, and `blockMinutesFor` is pure. Prunes finished rows on each recorded failure |
| `lib/auth/client-ip.js` | Reads the client address from `x-forwarded-for`. **Rate limiting only, never authorisation** — the header is only trustworthy because the platform's proxy rewrites it. Unattributable requests share one bucket rather than being waved through |
| `lib/auth/admin-users.js` | **The credential check.** `authenticateAdmin(email, password)` — matched on `lower(email)`, and an unknown address is verified against a decoy hash so that it costs the same as a wrong password. Returns the account or null, never a reason |
| `lib/public-routes.js` | **Which public paths the sitemap offers, and which it never will.** Three lists — built, generated per record, excluded on purpose — and nothing else; no imports at all, because `scripts/check-sitemap.mjs` loads it with plain Node. It exists so that a stub cannot be listed by forgetting and a finished page cannot be omitted by forgetting; the check enforces both |
| `lib/site-url.js` | **The only reader of `NEXT_PUBLIC_SITE_URL`**, and the only place a path becomes absolute. `absoluteUrl` returns an already-absolute URL untouched, which is not tidiness: an artwork page's share image is the painting, and a painting the artist uploaded is already `https://…`, so prefixing the site address produced a preview that resolved to nothing. Canonical URLs, hreflang pairs, the sitemap and share images are absolute by definition. Throws in production when it is unset, because a wrong base publishes a canonical pointing elsewhere and nobody finds out for weeks; falls back to the dev server address on a laptop |
| `lib/translate.js` | **The only place the translation key is read**, and server-side only. Hebrew in, English out, for the admin work form. Named for the job rather than for the provider, **which has already paid for itself**: DeepL stopped selling its free plan, and the move to Gemini changed this file and nothing above it. It owns the model — pinned, never a `-latest` alias — and the instruction, which is half the module now that the provider is a language model rather than a translation engine: a title has to come back a noun phrase and a description as prose, so `TRANSLATION_KINDS` is the closed set the caller picks from. **It never throws**: no key, a wrong key, a timeout and an exhausted quota all come back as `{ ok: false }`, because a translation service having a bad afternoon must not be able to trap the artist in a form. `isTranslationConfigured()` is what lets the form leave the feature out entirely rather than fail at every field |
| `lib/image-host.js` | **The only place the image-host credentials are read**, and server-side only. Named for the job rather than the provider, like `lib/translate.js`. Two halves, because **the file never passes through this server**: `signImageUpload()` authorises one upload into one fixed folder, and `readUploadedImage(publicId)` asks the host what actually arrived. That second half is the point — the browser's report of a width, a height and a URL is a claim, and pixel dimensions are what reserves the box a painting is drawn in. Signed rather than an unsigned preset: a preset is a public write endpoint into her media library, named in the page source. Owns the free plan's limits (10MB, 25 megapixels) and, like translate, **never throws** — every failure is `{ ok: false, error }` with a code the admin says in Hebrew |
| `lib/image-loader.js` | **The one place a stored reference becomes a URL the browser fetches**, wired in as `images.loaderFile` so every `next/image` goes through it and no component knows about any of this. Decides per image, by the same leading-slash test the repository uses: a hosted painting is resized **by the host** via a transformation written into its URL, a local file keeps Next's built-in optimiser. Owns `c_limit` — **the never-crop rule at the delivery layer**, and the only expression of that rule that cannot be seen to break, which is why `scripts/check-image-crop.mjs` exists. Loaded by the browser, so it imports nothing |
| `lib/revalidate.js` | **Clearing the public site's caches, in one place**, and the single point every writer goes through. `revalidatePublicSite()` does two things that are not interchangeable: `revalidatePath('/', 'layout')` for the homepage, which is a prerendered page held by path, and `revalidateTag(WORKS_CACHE_TAG, 'max')` for the gallery's catalogue read, which is a data-cache entry held by tag. A write that clears one and not the other leaves the site half stale, and which half depends on which page you open — so no caller gets to pick. **Not `updateTag`**, which is Server-Action-only: this is shared with the payment return, a route handler. The path invalidation is deliberately blunt rather than a per-action list of routes in two languages, because forgetting an entry means offering a painting that sold. Called by all nine admin mutations and by the verified-success branch of the payment return |
| `lib/cart/cart-contents.js` | **What a cart is, as a value**, and the pure half of the pair — no `next/headers`, no request, no database, loadable by plain Node. Parses and serialises the cookie value, adds, removes, and adds up. **A cart holds work ids and nothing else**: not titles, not prices, not availability, because every one of those is re-read from the database on each render — commerce.md's "a cart is a wish, not a hold", made structural. Owns `MAX_CART_ITEMS` (a cookie dies near 4KB), the uuid shape check that drops anything hand-edited, `chargeableAmount` (the one place a reduced price wins), and `readCookieValue`, which exists because the header's count parses `document.cookie` in the browser |
| `lib/cart/cart-cookie.js` | The request-facing half: `readCartIds`, `writeCartIds`. The one place the cookie's attributes are set. **Deliberately not `httpOnly`** — the count in the header reads it, and the alternative was reading the cart in the public layout, which opts *every public page* out of static rendering to draw one numeral. Nothing is risked by that because nothing trusts the cookie. An empty cart deletes it rather than storing an empty string |
| `lib/data/orders-repository.js` | **The second data module**, and the only one that writes `orders`. `quoteCheckout` prices a basket without writing anything; `createPendingOrder` re-prices it inside a transaction with the works locked `for update`, refuses outright if anything has gone, and writes the order and its lines together. **Every amount in it is agorot**, read from `price_agorot` and written to `total_agorot` — it hands callers both the integer to be charged and a major-unit copy to print, so nothing above it has any reason to do money arithmetic. It prices **every** delivery method rather than the chosen one, which is what keeps the browser from adding a fee to a subtotal. The order's `gen_random_uuid()` id is its public reference and what goes in Hyp's `Order` parameter. `createPendingOrder` writes no payment state and marks nothing sold. **`settlePaidOrder` is the one that does**, after a verified return: it locks the order, short-circuits on a replay, seizes every painting by one conditional statement (`status = 'available'`, the row count deciding, all-or-nothing), and only then marks the order paid. It deliberately does **not** reuse `markWorkSold`, whose channel guard would misread a replay as a lost race. `recordUnfulfillableOrder` writes the losing branch — `cancelled` if the charge was voided, `paid` plus `refund_due_at` if it could not be — and if the reference collides it writes the obligation anyway, without the reference, because money owed matters more than the id it is owed under. `getOrderForConfirmation` joins the lines to `works` for their titles rather than re-reading them public-scoped, so unpublishing a painting cannot erase it from a receipt. The admin's pages add `getOrdersForAdmin` (which computes the stale-pending and refund-owed flags in SQL), `getOrderForAdmin`, `advanceOrder` — whose `where` clause can only match a legal transition, so the UI cannot produce a row the schema would refuse — and `closeOrder`, the two exits. **`closeOrder` deliberately does not use `returnWorkToSale`**: that one excludes `sale_channel = 'this-site'` so the works list cannot undo a site sale by hand, and every painting sold through checkout carries exactly that channel, so calling it here would match nothing and leave a refunded painting marked sold. It also **releases nothing for an order that owes a refund** — that painting was won by another buyer, and taking it back would be the worst possible way to fix a refund |
| `lib/payments/hyp.js` | **The only place the payment credentials are read**, server-side only, and named for the provider rather than the job because the flow is Hyp's and cannot be swapped without a decision. **We do not compute the signature — Hyp does**: a GET to `…/p/?action=APISign&What=SIGN` returns a query string already carrying `action=pay` and `signature=`, and it is appended to `…/p/?` **verbatim**, never parsed and rebuilt, because its parameter order is part of what the signature covers. Converts agorot to the provider's decimal `Amount` — the one conversion on the charging path. **Never throws**: every failure is `{ ok: false, error }`. Refuses outright, outside production, to sign against a terminal that is not a test terminal. It also owns the way back: `verifyReturn` replays the redirect's query **verbatim and in its original order** behind our credentials, `cancelTransaction` is the same-day void, and `interpretVerifyResponse` is the pure, exported judgement — `CCode` decides, never HTTP status; HTML means a system error; anything unreadable fails. **Missing credentials answer `cannotVerify`**, which is its own outcome precisely so it can never collapse into success. Carries `HYP_ENDPOINT_OVERRIDE`, a development-only seam ignored in production, which exists so all of that could be proven before the account existed |
| `lib/payments/handle-return.js` | **The whole of how this application learns that money moved.** Shared by both return routes. VERIFY first and nothing before it; a failed, forged or unverifiable return changes nothing anywhere and the buyer is told the payment is not confirmed. On a verified success it settles the order and **clears the cart here and nowhere else on this path**, deleted on the redirect response itself. On the race branch it attempts the void, records which outcome happened, and deliberately leaves the cart alone — nothing was sold to this buyer. A verified payment naming no order is logged at full volume rather than guessed at. **On a verified success it also calls `revalidatePublicSite()`** — it is the only writer of `status = 'sold'` outside the admin, and without that the cached homepage and gallery would go on offering a painting for up to an hour after it sold |
| `lib/checkout/checkout-input.js` | Validates the checkout form. Pure, plain-Node loadable, error **codes** not sentences, and it keeps the typed values so a rejection does not empty the boxes. Composes the structured address fields into the one `shipping_address` column, and returns null for self-pickup because the database requires the absence. No email regex, deliberately; the postal code is checked because a wrong one is a parcel that does not arrive |
| `lib/checkout/actions.js` | **The checkout Server Action.** Validates, creates the pending order, signs the payment page, redirects — in that order, because an order must exist before the buyer reaches payment. No session check, and that is not an omission: checkout is guest checkout. It trusts nothing instead — the work ids come from the server's own cookie or a **bound** argument, never from the submitted form, and so does the locale. It does **not** clear the cart: nothing has been paid for |
| `lib/cart/actions.js` | **The cart's four Server Actions**: read, add, remove, and clear the works that no longer resolve. Each re-reads the work from the database public-scoped and re-checks it is buyable, so a painting sold on another platform cannot be added however long its id has sat in a browser. **They return the cart rather than redirecting** — the drawer opens in place and never navigates, so it needs the new contents back; `/cart` still works unchanged because a form whose action returns a value still re-renders the route it posted from, and that page re-reads the cookie anyway. `notice` comes back as a **code**, never a sentence. No session check, and that is not an omission: these are public, and the only thing they change is the caller's own cookie. It lives in `lib/cart/` rather than the route folder so the whole cart is one directory |
| `lib/db.js` | **Owns the database connection.** One pooled `pg` client behind `getPool()`, created on first use and cached on `globalThis` so hot reload cannot leak pools. Throws with instructions when `DATABASE_URL` is missing. Server-side only, and **`works-repository.js` is its only importer**. This module owns the connection and runs no queries of its own; nothing else may create a pool |

## Scripts

| File | Role |
|---|---|
| `scripts/generate-image-manifest.mjs` | Reads JPEG/PNG headers in `public/paintings/` and writes the manifest. No dependencies. Wired into `prebuild` |
| `scripts/check-contrast.mjs` | **The palette guard.** Computes WCAG contrast for every permitted pairing and asserts the forbidden ones stay forbidden. Reads values from `app/tokens.css`. Runs with `npm run lint` and on its own as `npm run check:contrast`. Not in the build |
| `scripts/generate-dev-placeholders.mjs` | Writes the three placeholder paintings for `/dev`. Encodes PNG by hand and reads its two colours out of `app/tokens.css`, so the files can never drift from the palette. No dependencies. **Not** wired into `prebuild` — the output is committed |
| `scripts/check-admin-guard.mjs` | **The guard guard.** Fails if any `page.js` under `app/(admin)/admin/(guarded)/` does not import and call `requireAdminSession`. It exists because the guard is called per page, so a new page could silently be added without one. Runs with `npm run lint`, or alone as `npm run check:guard`. Same shape as the contrast guard: no dependencies, prints a table, not in the build |
| `scripts/check-image-crop.mjs` | **The crop guard**, and the fourth of them. Asserts that every width the loader emits is `c_limit` and width-only, that no cropping mode appears, that a local file still reaches the built-in optimiser untransformed, and that an unrecognised reference is passed through rather than rewritten. It exists because the delivery layer is the one place the never-crop rule breaks **invisibly** — a cropped file looks perfectly correct inside a correctly-built frame. `npm run check:crop` |
| `scripts/check-sitemap.mjs` | **The sitemap guard.** Asserts that every `page.js` under `app/(site)/[locale]/` is exactly one of three things — a stub, a declared exclusion, or listed in `lib/public-routes.js`. "Stub" means it renders `components/ui/StubPage`, so a page stops being one by the act of being built. Catches a stub that would be indexed *and* a finished page silently missing. Same shape as the other two guards: no dependencies, prints a table, not in the build. `npm run check:sitemap` |
| `scripts/create-admin-user.mjs` | **The only way an admin account comes into being.** Creates one or replaces its password. The email may be an argument; the password never is — it is typed with the echo off, and the script refuses to run without a terminal so it cannot be piped one either. Unlike the seed script it is **not** local-only, because the real accounts had to reach Neon; a non-loopback host is named and confirmed instead of refused. **Both accounts exist in Neon as of 12-09-2026.** Reads the row back and verifies it before reporting success. `npm run admin:create` |
| `scripts/seed-local-database.mjs` | **Local development only.** Fills a local database with the sixteen works from `artworks.js` plus their images. Refuses to run unless `DATABASE_URL` points at loopback, and also refuses on `NODE_ENV=production` or on a build host — Netlify and Vercel are both named, because an unrecognised platform sets neither marker and the guard would go quiet with nothing to say so. The check runs before any connection opens. Idempotent: works upsert on `slug_en`, images are replaced, all in one transaction. Deliberately **not** in `database/migrations/` and deliberately **unnumbered**. `npm run seed:local` |

## Database — `database/migrations/`

Plain SQL, applied by hand in pgAdmin or with `psql`, in numeric order. No
runner, no ORM, forward-only, ASCII-only. Conventions and the full schema are in
database.md. Which migrations a given database has had applied is not recorded
anywhere — ask the database.

| File | Role |
|---|---|
| `001_create_works_table.sql` | `works`. uuid key, slug per language, the four statuses, `published_at` as a separate axis, optional reduced price, at most one featured work |
| `002_create_work_images_table.sql` | `work_images`. Several rows per work, `image_ref`, pixel dimensions, type, position, optional alt text. At most one `main` per work |
| `003_create_orders_tables.sql` | `orders` and `order_lines`. No quantity column, no repeated work in an order, and an ordered work cannot be deleted |
| `004_create_admin_users_table.sql` | `admin_users`. Hash only, case-insensitive email uniqueness, no role column, no reset fields |
| `005_add_order_buyer_locale.sql` | Adds `orders.buyer_locale`, required, constrained to the locales in `lib/i18n/config.js` |
| `006_add_admin_login_throttle.sql` | `admin_login_attempts`. The sign-in rate limit's counter — the policy 004 deferred. References nothing on purpose, two partial unique indexes, no thresholds in the SQL |
| `007_add_order_status_dates.sql` | Adds `delivered` as a sixth order status and the five dates each status happened. **The 14-day cancellation window, made computable** — the law counts from receipt, so `shipped_at` alone could never answer it. Enforces the forward chain (`paid` needs `paid_at`, `refunded` too; `delivered` needs all three; `pending` needs none) and their order, and is deliberately silent on the two exits. **009 narrows one of those rules**: a self-pickup order never ships, so `delivered` needs a dispatch date only when the method is shipping. The one place the schema ties a status to another column, where `works.sale_channel` deliberately does not — the comment says why at length |
| `010_add_order_refund_due.sql` | **`refund_due_at`** — the one state the payment return had nowhere to put: money taken, the painting gone to somebody else, and the charge impossible to void. The order stays `paid` (it is) and this says a refund is owed on top. Not a seventh status, because 007 requires `paid_at` before `refunded` and an order that never passed through paid could never be marked refunded without inventing a payment date. A timestamp rather than a boolean so the admin can sort by how long it has been owed, and a partial index because that is a question about the few rows where it is set |
| `009_add_order_delivery.sql` | **How an order reaches its buyer, and what that cost.** Adds `delivery_method` (`shipping` \| `self-pickup`, required, no default) and `delivery_fee_agorot` (required, minor units, **stored so a rate change cannot rewrite an old order**). | `008_load_catalogue_data.sql` | **The catalogue itself, as data** — the sixteen works and their images, so a fresh Neon can be brought to exactly what the local database holds. ## Not built yet

Gallery pagination.

**The purchase flow itself is built end to end** — the checkout, the pending
order, the signed payment page, the redirect out, VERIFY on the way back, the
conditional seizure, the paid mark, the cart clearing, the confirmation page, and
the admin's two orders pages.

What it has never met is Hyp. There is no account yet, so all of it is proven
against a local stand-in; deployment.md holds the exact ledger of what that does
and does not establish, and the terminal tasks for the day the account exists.

Add them here as they land.

**The cart is built, as a drawer.** Adding a painting from its own page slides a
panel in from the edge of the screen and never navigates. It re-verifies every
work against the database each time it is drawn, excludes anything unbuyable
from the total with a sentence saying why, and ends in a **checkout button that
deliberately does nothing** — no provider is chosen and `/checkout` is a stub.
`/cart` is still the whole page, server-rendered, works with no script, and is
linked from the foot of the panel; it is the surface a real checkout should grow
on.

**Adding needs JavaScript now, and that is a reversal worth knowing about.** The
first version was a plain form post that worked with script off and redirected
to `/cart`. A panel that opens in place cannot be done without script, so that
was traded away on purpose — with `/cart` kept precisely so nothing is actually
unreachable.

Two known gaps around it, both recorded rather than forgotten:

- **A discounted work would read two ways.** `cartTotal` charges the reduced
  price, because that is what would actually be charged; `Price` renders
  `amount` and says nothing about a reduction, because commerce.md leaves
  discount presentation undecided. No work carries one today, so the
  disagreement is dormant — deciding the presentation closes it.
- **Marking a work sold from the works list is now built**, which closes the
  third mitigation and the one the other two depended on. The cart catches a
  stale work at render and again on add — worth exactly as much as the status in
  the database is current, and keeping it current no longer means opening the
  edit form and getting past its translation gate.

**Image hosting has landed, for the main image only.** The artist can attach or
replace one photograph per work from the edit page, and it goes to Cloudinary
rather than into the repository. What is still missing around it: `detail` and
`in-situ` images, which the schema and the artwork page already accommodate;
any way to *remove* an image without replacing it; and the previous file on the
host, which is deliberately left behind rather than deleted — see images.md.

One gap the artwork page ran into and did not close: `work_images.alt_he` /
`alt_en` are still not read by the repository, so alt text is derived from the
work's title per image role. The upload does not write them either, for the same
reason: absent means "derive it from the title", and a default would be a phrase
living in the database instead of in the locale files.

Two more that seo.md wants and nothing has yet: **structured data** anywhere, and
**hreflang on the public pages other than the artwork route**. The second cannot
be done in the layout — a layout cannot know which page was requested, see
frontend/next.md — so it is a per-page addition. The sitemap already declares the
alternates for all of them.

The admin is guarded, but **only where it renders**. Every mutation there checks
the session in its own first lines, and so does every action that spends money
or authorises a write somewhere else — signing an upload is on that list. See
security.md.

**The site reads Postgres.** Every page goes through `works-repository.js`, which
queries the database through `lib/db.js`; `artworks.js` is now only the seed
fixture and the home of the shared constants. What the swap had to reconcile —
minor units, the uuid key, the publication filter, medium — is in data-layer.md,
and those reconciliations are live code now rather than a plan.

Development runs against a local Postgres. **Neon carries the production schema
now** — 001 through 010, the catalogue and both admin accounts, since
12-09-2026 — but nothing is deployed against it, so `DATABASE_URL` is set on no
host. See database.md.

When the sitemap lands it needs no `/dev` exclusion: generated from the locale
list and the works repository, as seo.md requires, it cannot emit a URL outside
`app/(site)/[locale]`.
